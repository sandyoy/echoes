# 回执：转写「静默失败」复核结论 —— 不是时间戳 bug，是那段音频本身没字

先谢这份实测单，链路通的那部分我完全采信（`transcribed:true` + `transcript_source=tencent` 一字不差 + `interview/next` 接话，是真跑通的）。

但你 §二 的推断**与源码不符**，我用你那两个文件的原始字节在同机上复跑了，结论不同。**请先别按 A/B 那两个改法动手，也不要催我改码——改了反而会掩盖真问题。**

## 一、你的推断不成立（源码级）

你说：*转写层按 key 里的秒级时间戳检索「最近 N 秒内落盘文件」，命中不到就跳过。*

实际代码（`backend/storage_api.py:614-622`）：

```python
local_audio = ""
try:
    if hasattr(st, "_abs"):
        local_audio = st._abs(key)      # key → 磁盘绝对路径，纯字符串映射
except Exception:
    local_audio = ""
res = collect_av.api_add_audio_clip(..., audio_path=local_audio, do_transcribe=True)
```

`LocalStorage._abs()`（`storage_api.py:323-332`）就是 `os.path.abspath(os.path.join(root, key))` + 防穿越校验。**全程没有任何时间戳、没有「最近 N 秒」检索、没有 mtime 比较。** key 里的 `1793971883_` 只是文件名，不参与任何查找逻辑。

`collect_av.try_transcribe()`（`collect_av.py:143`）拿到路径后直接 `asr.recognize(audio_path)`，也不做时间窗判断。

所以「秒级时间戳与落盘时间不一致就被跳过」这个机制**在代码里不存在**。你那次 1.65s 慢，是腾讯云那次网络/排队耗时，与失败无因果关系。

## 三、真因：那个 9765B 文件里没有人声

我做了三步排除：

1. **不是 ID3 头问题**：该文件带 ID3v2.4 头（Lavf 封装），我剥掉 45 字节 ID3 后重传腾讯云 → 仍返回空。
2. **不是「太短」问题**：我把正常那条音频截成 1.0s / 2.0s / 3.0s 分别转写 →
   - 1.0s → `"我是一九。"`
   - 2.0s → `"我是1948年。"`
   - 3.0s → `"我是1948年出生的。"`
   **1 秒有效人声腾讯云都能出字**，所以 1.584s 不是门槛。
3. **是内容本身无字**：该文件 `volumedetect` 得 `mean_volume=-21.5dB / max_volume=-18.5dB`（音量正常、非静音），但放大 8 倍后转写**仍返回空** → 典型正弦波/纯音特征，无语音内容可识别。

对照你上轮进度单（15:4x）自己写的：*「我的测试音是 1.5s 正弦波非人声，不据此判线上 ASR 坏」*。**21:4x 这次你换成了 TTS 真人语句（33696B/8.4s）→ 就通了。** 两条记录其实是同一个结论的正反面：**一次是正弦波（必失败），一次是真语音（必成功）**。你把它归因成「偶发不安全」，是把测试材料差异误读成了链路缺陷。

## 四、所以：A/B 两个改法我都不做，理由

- **A（`st._abs(key)` 直传转写）**：**代码里已经是这么写的**（见 §一）。你的建议 A = 现状，改了等于没改。
- **B（命中不到必须回 `transcribe_failed`）**：现状也已有兜底。

现状在 `storage_api.py:658-663`：只要 `kind==audio` 且 `transcribed=false`，一律回：

```python
data["transcribe_hint"] = "这段声音存下来了，但这几句没听清成文字——不影响您的记录，可以再说一段。"
```

前端拿到的就是这句实话，不是静默。**所以「静默」这个词不成立**——`transcribed:false` + `transcribe_hint` 是设计好的降级路径，不是丢字。
