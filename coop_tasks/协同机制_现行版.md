## 一、上传区：各放各的，永不共用（核心铁律）

| 谁 | 写文件的地盘 |
|---|---|
| 小龙虾（本地） | `coop_tasks/` 里以 `小龙虾` 开头的文件；产出物放 `docs/` 下自己负责的目录 |
| 小鲸鱼（云端） | `coop_tasks/` 里以 `小鲸鱼` 开头的文件；产出物放自己负责的目录 |

- 双方都能 `git pull` 看到对方的所有文件 ✅
- **但绝不往对方名下的文件里写** ❌
- **绝不覆盖对方已存在的文件** ❌

### 日期型日志必须带自己的名字（防撞车）
```
docs/daily/盯催日志_小龙虾_20260918.md      ← 只写自己的
docs/daily/盯催日志_小鲸鱼_20260918.md      ← 只写自己的
docs/pull_log/pull_小龙虾_20260918.md
docs/pull_log/pull_小鲸鱼_20260918.md
```
❌ 禁止再出现 `盯催日志_20260918.md`（无主文件）这种共用文件——那是今天互相覆盖的根源。

### 空转不写文件（防噪音）
- **没有实质变更，不写任何日志文件。**
- 定时任务只在"拉到新东西 / 有新任务 / 完成工作 / 出现异常"时才留痕。
- 目的：仓库里留下的每一条都是真信息，sandy 一眼能看出我们干了什么。

## 二、改稿流程：改对方写的东西，只有两条路

sandy 让改「对方写的文件」时：

### 方式一（推荐 · 默认）：提要点，由原作者改
- 改动方 → 写一份 `XX请改_文件名_日期.md`（或直接发任务单），**只列要点和理由**
- 原作者 → 按要点改自己的原文，更新版本号
- ✅ 好处：版本链不断，原作者最清楚上下文

### 方式二：直接改，但成果放自己那儿
- 改动方直接改，**改完的成品放到自己名下**，用新文件名（如 `_小鲸鱼改版`）
- ❌ **绝不覆盖原作者的文件**
- 原作者决定是否吸收

### 铁律
- **谁都不许覆盖对方的任何文件。**
- 拿不准用哪种方式 → 默认走**方式一**。

## 三、任务传递（沿用 8-29 机制）

- 待办统一放 `~/echoes/coop_tasks/`
- 命名带方向：`小龙虾请做_xxx_日期.md`（小鲸鱼→小龙虾）/ `小鲸鱼请做_xxx_日期.md`（小龙虾→小鲸鱼）
- frontmatter 必须有：`status`（待认领/进行中/已完成）、`assignee`、`requester`、`created`
- 认领 → 干活 → 填**完成回报** → push
- 不抢对方已认领的活（看 status）
- 做不了的（本地/云端环境限制）如实派回对方，不硬扛、不沉默

## 四、执行铁律
1. 干活前先 `git pull`；干完 `git push`，并 `git fetch origin main && git status` **验证真的推上去了**
2. 谁认领谁负责到底，做完必须写完成回报
3. 改文档必须**整段替换 + 改完通篇复查**，禁止只改局部留下旧内容残留
4. 定时任务**静默运行**，只在真有进展/异常时才通知 sandy
5. 分工：前端/本地/预览码归小龙虾；后端/云端/ASR/云存储归小鲸鱼
