# 功能需求表 · 院外延伸服务管理模块（暂定名）

**版本：** v1.0　**日期：** 2026-09-21　**编制：** 云端 Hermes（小鲸鱼）　**提交对象：** sandy → 技术团队

---

## 第 0 页 · 三句前置声明（请技术团队先读这一页）

**① 这个模块是"工具"，不是"服务"。**
圆爱康**不做上门服务、不派自己的人上门施治、不承担医疗行为责任**。本模块只是给**已经有上门能力的合作医院/合作机构**使用的一套管理系统，帮他们把人、证、单、记录、数据管起来。**服务主体永远是医院/合作机构，不是圆爱康。**

**② 本模块对外"暂不宣传"。**
开发阶段及投用初期，官方资料、官网、销售 PPT、演示环境**一律不出现"上门""上门服务""上门医疗"等字样**。定位是"内部弹药"，先做不先说。对外统一口径仍为"居家康复（设备回家 + 远程系统 + 医院医师协同）"。

**③ 本表是"讨论底稿"，不是定案。**
本表由业务方提出"整体想象力"，**技术团队可增删、可砍优先级、可指出已有能力**。请对照本表逐项给出：能做到 / 已有 / 需改造 / 不建议做 / 工期粗估。

## 一、为什么要有这个模块（业务背景，一句话版）

合作医院已经在做（或想做）院外/居家延伸服务，但**过程不可视、记录不可查、资质不可控、责任不可分**。
本模块解决的是：**让医院敢做、能留痕、能举证、能把数据带回来。**
而数据回传本身，正好接回圆爱康已有的护城河（治疗数据闭环 + 六师共管）。

**与现有 CMS 的关系：** 本模块是 **CMS 的一个子模块**，不另起一套系统。CMS 已有：患者档案、随访、治疗数据、医护 PC 端、医生管理小程序、患者预约小程序——本模块复用这些底座，只新增"院外服务"这一段。

---

## 二、三路线责任划分（本模块存在的前提，**必须先钉死**）

| 路线 | 谁在做上门 | 资质要求 | 圆爱康角色 | 是否本期范围 |
|---|---|---|---|---|
| **A. 服务提供者** | 圆爱康自己派人上门施治 | 必须有（医疗机构执业许可/护士执业证等） | ❌ 永不进入 | ❌ 不在范围 |
| **B. 系统/工具方** | 合作医院/机构 | 资质在服务方 | ✅ **本模块就是这一条** | ✅ 本期要做 |
| **C. 交付动作**（送装/调试/教学，非诊疗） | 圆爱康或合作方 | 一般不需医疗资质，设备需注册证 | ✅ 可做 | ⚠️ 可考虑纳入，但话术上不叫"上门医疗" |

> **结论：本模块的所有设计，都必须服务于"责任在服务方、痕迹留系统里"这个原则。**

## 三、功能总览（分 P0 / P1 / P2 三层，可按层砍）

| 层 | 含义 | 说明 |
|---|---|---|
| **P0** | 必须有。没有它，这个系统不成立（做不了合规的院外服务） | 本期建议必做 |
| **P1** | 应该有。有它才"专业"，医院才愿意用 | 建议做，可分批 |
| **P2** | 加分项。锦上添花，未来再说 | 可直接砍或延后 |

## 四、核心功能需求表（详细）

### 模块 1：服务人员与资质管理（P0）

| 功能ID | 功能点 | 验收标准（可逐步测） | 依赖/联动（改它会牵动谁） | 优先级 |
|---|---|---|---|---|
| R1-1 | 院外服务人员台账 | 可新增/编辑/停用人员；字段含姓名、所属机构（**必填，默认=合作医院**）、岗位、联系电话、状态 | 与"机构管理"共用主体表；与派单模块绑定（无台账不能派单） | P0 |
| R1-2 | 资质证照登记 | 每人可上传多张证件（执业证/职称证/培训证），含证号、发证机关、有效期 | 与"到期预警"联动；与"派单拦截"联动 | P0 |
| R1-3 | 资质到期预警 | 距到期 30/15/7 天分级提醒（站内 + 可选短信/企微）；过期人员自动置为"不可派单" | 触发 R1-4、R2-2 | P0 |
| R1-4 | 派单资质拦截 | 派单时若人员无对应资质或已过期，系统**阻断派单**并提示原因 | 被 R2-2 调用；影响服务单状态机 | P0 |
| R1-5 | 服务范围授权 | 可设置某人能做的服务类型（如仅送装、仅护理、可施治），派单按范围过滤 | 与"服务项目库"（R4-1）联动 | P1 |
| R1-6 | 人员排班与可约时段 | 可维护人员周排班、请假、暂停接单 | 与派单抢占逻辑联动 | P1 |
| R1-7 | 资质合规报告导出 | 一键导出"当前人员资质汇总表"（用于医院迎检/自查） | 依赖 R1-1/R1-2 | P1 |

> ⚠️ 关键设计原则：**本模块只做"台账 + 校验"，绝不代替卫健部门/医院做资质认定。** 证件真伪由服务方负责，系统只记录+提醒。

### 模块 2：服务工单全流程（P0，核心）

| 功能ID | 功能点 | 验收标准 | 依赖/联动 | 优先级 |
|---|---|---|---|---|
| R2-1 | 工单创建 | 可从患者档案一键创建院外服务工单；字段含患者、服务项目、约定时间、地址、服务人员、备注 | 与 CMS 患者档案、处方/方案模块联动 | P0 |
| R2-2 | 工单派单 | 支持手动指派 + 按排班/范围推荐；走 R1-4 资质校验 | 依赖 R1 全模块 | P0 |
| R2-3 | 工单状态机 | 待派单 → 已派单 → 已接单 → 前往中 → 服务中 → 已完成 → 已完成确认 / 已取消；每步留操作人与时间戳 | 影响统计报表、消息通知 | P0 |
| R2-4 | 移动端执行（服务人员端） | 服务人员在手机上：接单、导航、到达打卡（定位）、开始/结束、填写记录、上传照片/附件 | 与"医护端小程序"技术栈复用；与文件上传服务联动 | P0 |
| R2-5 | 到岗与离岗打卡 | 记录到达时间/地点、离场时间/地点；异常（超时/异地）标记 | 与 R2-3 状态机联动 | P0 |
| R2-6 | 服务记录填写 | 结构化表单：做了什么、患者状态、器械使用、异常情况、下次建议；支持模板按服务类型自动带出 | 与"服务项目库"（R4-1）联动 | P0 |
| R2-7 | 患者/家属确认签收 | 患者端（或服务人员端代签）签名确认，含确认时间；电子签名留档 | 与患者端联动；与"纠纷举证"（R6）联动 | P0 |
| R2-8 | 工单改期/取消 | 支持改期、取消，需填原因；留操作痕迹 | 影响排班占用、通知 | P1 |
| R2-9 | 工单超时与异常提醒 | 未按时接单/未打卡/长时间"服务中"未结束 → 提醒管理员 | 与管理端消息中心联动 | P1 |
| R2-10 | 多机构隔离 | 不同医院的数据互不可见（机构级数据沙箱） | **影响所有模块的查询条件**，务必早定 | P0 |

> ⚠️ R2-10 是架构级决策，建议技术团队优先确认：**数据是"多租户隔离"还是"单机构部署"**——这决定后面所有表的写法。

|---|---|---|---|---|

### 模块 4：服务项目与标准（P1）

| 功能ID | 功能点 | 验收标准 | 依赖/联动 | 优先级 |
|---|---|---|---|---|
| R4-1 | 服务项目库 | 可定义服务类型（如：居家康复指导/设备送装调试/护理操作/随访评估），每项含：名称、所需资质、标准时长、标准动作清单、需填记录项 | **是 R1-5、R2-6、R3-1 的共同上游**，改它会牵动一片 | P1 |

### 模块 5：数据回传与医疗闭环（P0，**圆爱康的护城河所在**）

| 功能ID | 功能点 | 验收标准 | 依赖/联动 | 优先级 |
|---|---|---|---|---|
| R5-1 | 服务记录回传患者档案 | 服务记录自动挂到该患者健康档案时间轴 | 依赖 CMS 患者档案；影响随访视图 | P0 |
| R5-2 | 设备数据与服务记录关联 | 若该患者有居家设备，服务记录可与设备治疗数据同屏展示 | 与物联网数据模块联动 | P1 |

## 五、非功能性要求（容易被忽略，但决定能不能真用）

| 项 | 要求 |
|---|---|
| 合规性 | 个人信息保护（健康数据属敏感个人信息）、数据出域需协议约定；服务人员定位采集需患者知情 |
| 性能 | 服务人员端以移动端为主，弱网可用（断网可暂存、联网补传） |
| 终端 | 复用现有技术栈：医护 PC 端 + 小程序 + 患者端，不新起技术路线 |
| 定位 | 定位仅在服务过程中采集，服务结束即停；不后台常驻 |
| 可维护 | 服务项目、话术、表单模板必须配置化，不能让技术每次改代码 |
| 多租户 | 与 R2-10 一致：机构间数据隔离 |

## 七、"对外什么时候可以提"的解禁判断标准（内部备忘，不放对外材料）

**三条同时满足才考虑对外提：**
1. 已有一家合作医院**真实在用**（不是演示，是真跑工单）；
2. 系统里的**资质校验 + 全链路留痕 + 责任边界声明**三条真跑通、能举证；
3. **协议/合同层面**已把"服务主体=医院、圆爱康=系统提供方"写清楚。

三条未齐前：**对外一律"居家康复"口径，不出现"上门"。**

## 八、附：与已有能力的关系（避免重复开发）
