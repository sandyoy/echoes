## 一、这份规则是干什么的

我们的仓库文件曾经混放在一起、没区分谁写的、谁在持续维护，导致：
- 翻找困难（不知道东西归谁、最新在哪个区）；
- 接力时容易覆盖对方最新版；
- sandy 夹在两个 Hermes 中间，靠记忆分不清谁做了什么。

本规则的目的是：**让仓库有清晰归属、双方都遵守同一套约定、任何一方凭"关键词"都能反查到产出**，不靠死记文件名。

成品区固定在 `docs/双Hermes/` 下，两条通道 + 一个总索引：

## 五、文档交接与演进的归属规则（最重要的一条）

> 这是最容易乱、也最容易引发"文档到底属于谁"争论的场景，单独成节讲清楚。

**判断准则一句话：**
> **"一份文档现在归谁，看'谁在持续演进它 / 谁手里有它的最新版'，不跟'最初是谁写的'走；换手时，在总索引里记一笔溯源。"**

下面三种具体场景，归属这样定：

### 场景一：原作文档（小龙虾/小鲸鱼写的）→ 交给对方演进成一个新成果（承接式）
- 最初由某方写了文档A。后来 sandy 拿它给另一方看，另一方读了、跟 sandy 继续讨论、在其基础上做出了更新的成果B；
- 那么成果 B 放进**【实际演进它、对它负责的那一方】的专属区**（例如小龙虾原作 → 小鲸鱼演进出 B，B 放小鲸鱼区）；
- 同时，在总索引里登记一笔溯源：**"B 源自某区的文档 A，某年某月某日由某人演进"** —— 让原作者能看到自己的作品被用在哪、演进成了什么，不断掉溯源。

### 场景二：演着演着，变成两端都持续维护的"共同主线/项目底稿"（并入式）
- 如果演进后的成果，是 sandy 和两个 Hermes 都会长期反复去改的项目主线（如 Echoes 小程序、某个三方共用的大方案底稿）；
- 这类**【不进任何一方个人专属区】**（放进某方专属区，会导致另一方无法顺理成章持续维护，还会引发互越区）；
- 放**项目自己的固定公共目录**，两个 Hermes 通过总索引指向它；个人专属区只放"我推导的成果"，不放"双方共同主线的活文件"。

### 场景三：另一方只是"读 + 讨论"，没有产生新版本（只读引用式）
- sandy 拿原作文档 A 给另一方看，另一方只是读它、陪解读或咨询，讨论完没有产出更新的成果；
- 那么 A 原样不动，继续挂在 **原作者区**（没有换手）；若讨论方另产出了配套解读/新的独立成果，那个新成果才放进讨论方自己的区。

**一句话收束：**
> 文档跟"持续演进它的人"走；不跟"最初写它的人"走；一换手就在总索引记一笔"源自谁/何时/谁演进"。个人专属区只放属于自己的推导成果，共同主线的文件放公共项目目录，靠索引指向。

## 六、必须共同遵守的通则

- **先 pull 再 push**：每次动手前先在共享仓库 git pull 同步，避免覆盖对方最新内容；
- **成品才入库**：只有"已定稿、能对外给对方看的成品"才进 `docs/双Hermes/`；中间过程稿、未定稿、每日流水，一律进临时/对账区；
- **各写各区**：小鲸鱼只写小鲸鱼区，小龙虾只写小龙虾区，两人均可在总索引登记；需要接力时用"给对方留任务条"的方式，不直接改对方区文件；
- **冲突不硬解**：发生仓库分叉或版本冲突时，不擅自强行覆盖对方，停下来知会对方商量处理；
- **旧的混放逐步清理**：已分散在公共大目录的成品，双方"谁属谁的、归到谁区"，认领后逐步搬入对应区，公共区只保留未清理完成前的过渡内容。
