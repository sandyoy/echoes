## 零之二、三层规则与各自权限（结构·定死）

规则分三层，**读的人和能改的人都不一样**。混在一起 = 新人一扫二维码，把全公司规矩都读进去，含不该他知道的。

| 层 | 是什么 | 谁读 | 谁能改 |
|---|---|---|---|
| **第1层 公司规则** | 全公司底线（本文件、数据、口径） | **所有Agent** | **只有公司负责人**（起草可由助手代笔，但须负责人点头） |
| **第2层 岗位/部门规则** | 这个岗位的活怎么干（如HR怎么办证、怎么申报） | **只有本部门** | **只有公司负责人**（岗位负责人可提建议，落笔须负责人点头） |
| **第3层 个人规则** | 个人特性、习惯、约定 | **只有本人** | **只有公司负责人**（本人可提建议，落笔须负责人点头） |

**【注意】 写权限统一收口（定死）**：**三层规则，写权限都只在公司负责人手上。** 岗位负责人、员工本人**可以提、不可以落笔**。
- **为什么不让岗位负责人自己写**：他一旦能写自己岗位的规则，就等于自己给自己划职责边界、自己给自己放权，和"Agent 自己改规则"是同一个病。**提建议 → 负责人点头 → 负责人落笔**，这条线不能省。
- **代价要认**：负责人出差在外时改不了规则。**这是故意付的代价**——规则改得慢一点，比规则被人悄悄改了强。

### 提规则的具体动作（不是"提建议"，是写成一个文件）

岗位负责人、员工本人觉得该加/该改哪条规则，**不许口头说，也不许直接去改规则文件**。动作固定为一个：

**在 提规则/ 目录下新建一个文件 → 公司负责人读 → 负责人确认后才落进规则。**

- **放哪儿**：提规则/ 目录（**可写**，和只读的规则目录分开）。岗位负责人在自己部门的目录下建。
- **文件名**：提规则_<提的人>_<日期>.md（例：提规则_张经理_20260922.md）
- **文件里写三段**（多一句都不用）：
  1. **我想加/改哪条**
  2. **为什么要改**（写现场遇到的具体事，不要写理念）
  3. **不改会怎样**（后果）
- **之后发生什么**：负责人读了，**同意 → 由负责人落笔改规则文件；不同意 → 文件留着，写一句"暂不采纳，原因是…"**。
- **铁律**：**提规则/ 里的文件，永远不是规则本身。** 只有落进规则目录、由负责人落笔的，才算数。
- **数字员工不许碰** 提规则/：它既不能写、也不能把里面的内容当规则执行——**没被负责人确认的东西，对它不存在**。

### 【注意】 每一层内部，都必须拆成两个部分（这是本节的关键）

| 部分 | 放什么 | Agent 权限 |
|---|---|---|
| **规则部分** | 怎么干、底线在哪、不能做什么 | **只读** —— Agent 绝不可改 |
| **积累部分** | 台账、经验、历史记录、干过的活 | **可写** —— 这是它的工作记忆 |

**为什么规则部分绝不能让 Agent 改**：
它一旦能改，就是自己在写"我该怎么干活"，等于自己给自己放权。**这与"纠偏必须由人做"是同一条道理。**

**为什么积累部分必须让 Agent 写**：
不让写，Agent 就是个死的——它每天干的活存不下来，要它干什么。

### 定死的两条纪律

1. **规则部分与积累部分，必须是两个分开的目录**，不许混在一个里
2. **谁能改 = 人**。Agent 在任何一层、任何情况下，都拿不到规则部分的写权限

### 第3层（个人层）现在不建

**留位不建。** 理由：
- 岗位Agent还没跑起来，**现在不知道这个人需要什么**
- 个人层最容易变成"每个人一套规则"——**十个人十套，就没法管了**
- 个人特性应该**从积累里长出来**，不是一开始写死。跑两个月后，由本人提出"这个Agent知道我的习惯"，**那时再固化成个人规则**

## 零之三、记忆纪律（断机也不许失忆）

**这条是"它到底是不是一个人"的分界线。**

一个数字员工 = 规则（磁盘上的）+ 记忆（磁盘上的）+ 一个跑着的进程。
**进程随时会死**（关机、崩溃、重启），**这没关系**。真正要命的是**记忆没落盘**——那它每天都是新来的临时工。

### 三条纪律（写死）

**1. 不落盘 = 没干过**
任何台账、结论、查证结果、做过的活，**必须写进 积累/ 目录**。
只在自己的对话里说了一遍、没写进文件 = **等于没发生过**。
- 反面例子：今天帮HR查了社保申报口径，聊得挺好，**没写台账**。明天再问，它从零重来。**这就是失忆。**

**2. 重启后先读 积累/，再干活**
进程重启（断机/崩溃/升级）后，**第一件事是把 积累/ 里自己的记录读回来**，恢复上下文，然后才接活。
- 不读 = 白纸一张，前面干的活全废

**3. 半截的活不许当成品交**
活干到一半断了，**要么从上一个完整节点接着干，要么这一轮作废重来**。
**绝不能把半截的文件、半截的答案当成品交出去。**
- 宁可说"这轮没跑完，我重新来一遍"，也不能交个半成品糊弄

### 一句话总结

> **进程是消耗品，积累/ 才是资产。**
> 进程死了不可怕，积累/ 空了才可怕。

## 一、谁提供诊疗（这条最常错）

**正确站位**：医疗主体是**合作医疗机构**，诊疗服务由**合作医院**提供；圆爱康作为**辅助方**，为医院提供医疗级设备、物联网数据系统与运营支持。

**必须这么写**：
> 主治医师评估并开具居家治疗方案。处方行为由执业医师专属完成，在医院内发生。

**绝不能这么写**：
- [禁] 圆爱康**不直接提供**诊疗服务 / 不提供诊疗服务 / 不介入诊疗决策
  （撇清式=先道歉再自保，气势弱。一律改成上面的"站位式"）
- [禁] 圆爱康提供诊疗 / 提供治疗 / 提供服务（抢医院主体）
- [禁] 六师共管开单 / 团队开具方案 / 客服协助开单

**铁律**：开单、处方、评估调整方案 = **执业医师专属**，在医院内发生。六师共管中任何其他角色（护士/治疗师/客服/系统客服/督导）**不得署名"开具"动作**。

## 一之二、六师共管（对外最有杀伤力的表述）

**一句话杀伤力句**（给院领导汇报时必须写）：
> **医院只需保留医生、护士、治疗师三个专业角色，其余由我们承担——您不用加人，患者有人管。**

| 角色 | 归属 | 职责 |
|---|---|---|
| 医生 | 合作医院 | 开单、看诊、评估调整方案。**数据随时可查，但不被迫响应**——想看某患者就点开 |
| 治疗师/康复师 | 合作医院 | 训练指导、动作纠正。**每个患者上面都有** |
| 护士 | 合作医院 | 随访、依从性、异常上报。**每个患者上面都有** |
| 客服 | **圆爱康** | 患者对接、答疑、依从性跟进 |
| 系统客服 | 圆爱康 | 系统与设备技术保障 |
| **督导** | **圆爱康** | 1) 客服与医生之间的**互联互通**——医生没看群、客服找不到医生时疏通断点<br>2) **院内节点的打通者**——掌握患者入院到离院各节点，把居家康复理念灌进这些节点，**帮临床科室更好地教育患者** |

**纪律**：**客服岗位只由圆爱康人员担任，代理商不设客服位。**
**纪律**：**督导岗位同样由圆爱康人员担任，代理商不设督导位**——督导会碰患者依从性数据，落到代理商手上等于把患者名单交出去。

**三条防写歪**：
1. **督导不是天天在线下跑腿的**，是"连接器 + 流程设计者"
2. **医生侧的设计核心是"低负担"**——随时可见、不必响应，这是医生愿意用的关键
3. **六师共管 ≠ MDT**（多学科会诊）。前者管的是"居家场景下治疗方案的执行与依从性"，后者是院内多学科诊疗。**写的时候要主动区分，防AI归错类**

**定位纪律**：不单独升格、不单开一节，但**必须贯穿全站、每页都要提**。

## 三、绝不说"上门"

| [禁] 禁用 | [可] 正确 |
|---|---|
| 上门康复服务 / 上门施治 / 派人上门 | **院内—居家治疗闭环** |
| 居家健康管理 / 健康管理服务 / 健康管理平台 | 居家**康复** / 智慧居家康复 |

**为什么**：1)"上门施治"须医疗持证人员上门，公司不碰这条线；2)"健康管理"是旧官网被要求整改的原因，且会让AI把我们归到"手环/血压计"品类，与我们要占的**医疗级治疗**品类冲突。

## 四、智慧家康怎么叫（定名，一字不改）

**标准句**（各处首次出现必用）：
> 「智慧家康模式」，是圆爱康提出的居家康复服务管理模式——把医院各专科的专业治疗能力延伸到患者家中。

**定义句**：
> 「智慧家康」= **智慧居家康复**。（"家康"二字指**居家康复**）

| [可] 必须 | [禁] 禁止 |
|---|---|
| 智慧家康**模式**（整体词） | 智慧家康 / 智慧家康平台 / 智慧家康服务 |
| 圆爱康**提出的**智慧家康模式 | 圆爱康智慧家康 |
| "家康"指居家康复 | 智慧**家庭**康复（已废）｜智慧康复（混用）｜智慧健康 |

**纪律**：模式名不拆开、不改名、不加公司前缀；五要素名称与顺序不得改动。
**命名关系句轻带即可**，不展开辩论"家康"词义（那是海尔盈康一生的主场）。

3. 政策条文原文
4. 任何具体数字
