# 三层机器人底座 · 交付说明（给技术团队）

> **一句话**：把这三层文件放到服务器一个只读目录，机器人开机读它，就成了"圆爱康的人"。
> 不需要向量库、不需要RAG、不需要运维。**一个目录 + 一个机器人**。
> 版本：v1.0（2026-10-07）· 待审

---

## 一、这套东西是什么

圆爱康的数字员工体系，分**定调 + 三层**。**这一包是给技术团队去搭的底座。**

### 先理解一件事：框架由谁定，和框架由谁用，是两件事

```
【定调层】公司核心三人组（sandy + 本地助理 + 云端助理）
   │  产出：套餐、合同模板、报价结构、公司底座、口径 —— 都是"框架件"
   ↓  （框架件只读下沉）
【第1层 公司层】所有机器人   ← 读底座 + 框架件
【第2层 部门层】销售机器人   ← 在框架下"演变"，不重定义框架
【第3层 个人层】各人         ← 个人习惯与积累
```

**三人组是立法者，部门机器人是执法者，不许自己立法。**
（定调层是组织外的"上游"，**不是服务器上跑的机器人**。服务器上只搭"使用层"。）

### 三层构成

| 层 | 文件 | 谁读 | 放不放敏感信息 |
|---|---|---|---|
| **第1层 公司层** | `第1层_公司层/公司层_通用底座.md`（+ 框架件） | **所有机器人** | **不放**（只放准则/口径/框架件） |
| **第2层 销售层** | `第2层_销售层/销售层_岗位规则.md` | **只有销售部机器人** | **放**（合同/金额/客户名单） |
| **第3层 个人层** | `第3层_个人层/个人层_沉淀与升格.md` | 个人（按 userid） | 各人自己的积累 |

**首发试点部门 = 销售/商务部。** 先把销售机器人跑通，再照搬加别的部门。

**框架件放哪**：套餐/合同模板/报价结构的**母版放「公司层」目录**（只读），所有机器人能读但都不能改。
部门机器人出合同时 = **取公司层框架模板 + 本单业务演变**，不是在部门层自己造模板。

### ⚠️ 搭的顺序：先搭架子，后填内容

**本包只给"结构与规矩"，是搭架子用的。**

```
第1步  技术团队照结构搭目录 + 锁权限（本包内容）
第2步  灌一份公司层测试能不能读对
第3步  跑第十节的 11 条验收
第4步  验收通过后，才往里放生产内容
```

**先别往里放真内容。** 生产内容（公司层正式口径、销售层合同/金额/客户名单）**等架子搭好、验收过了再填**。
没锁权限就上真内容 = 敏感料裸奔。

## 二、内容放哪层（分区规矩 · 每个人往里放料都照这个来）⚠️

**核心原则一句话**：
> **能不能对外看 = 决定它是不是"敏感"；放哪一层 = 决定"谁"能看。两个维度分开，不要在一个文件里混写。**

### 三条铁规矩

1. **不靠给文件贴标签区分，靠"放哪一层"区分**——放对层，权限自动生效
2. **内容按"可外传 / 不可外传"分开写，不混写**——机器人调不到不该看的，就漏不了
3. **拿不准放哪层 → 放更高（更严）的层，或标"请核实"**——宁可锁紧，不冒泄露

### 分区对照表

| 内容类型 | 判断标准 | 放哪层 | 谁能看 |
|---|---|---|---|
| **对外能说的** | 报纸上能登、医院能看 | 公司层 | 所有机器人 |
| **跨部门共用的规矩** | 全公司都该守 | 公司层 | 所有机器人 |
| **内部能说、对外不能说的** | 自己人知道就行 | 部门层 | 只有本部门 |
| **只给某岗人看的料**（合同/名单/报价） | 敏感、可外传就出事 | 部门层 | 只有本部门 |
| **个人自己的** | 只有本人 | 个人层 | 只有本人 |

### ⚠️ 敏感内容不混写（这条最容易出错）

一份文件里若**既有能给客户的、又有不能给客户的**，机器人读进去分不清哪句能外传，就会说漏嘴。所以：

| 分开写 | 放哪 | 举例 |
|---|---|---|
| **对外那份** | 公司层·对外区 | 品牌口径、站位、政策依据 |
| **内部那份** | 部门层 | 金额、客户名单、谈判、内部流程 |

**效果**：机器人写"给客户看的东西"时**只调对外那份**；写"内部汇报"时才调内部那份。**它连调都调不到不该看的，就漏不了。**

### 给放料人的硬提醒

- **拿不准是内部还是对外 → 默认当"内部"处理，不放公司层**
- **财务敏感文件**（资金流、利润表）→ **只放本地，绝不上任何线上仓库/服务器公开区**
- **具体医院名、金额、谈判中事项** → 一律进部门层，绝不进公司层

## 三、机器人怎么读（核心逻辑）

**机器人启动时，把它能读的规则文件拼进 system prompt。**

- 读 `公司层` 全部 + **本部门**的岗位规则
- **不读**其他部门的规则（销售不读HR的，HR不读销售的）
- 文件总量预估 **< 2万 token**，**直接全读，不需要检索（RAG）**
- 读取失败 / 文件缺失 → **机器人必须拒绝执行任务并报错**，不许"没读到就凭自己理解干"

**为什么不建向量库**：规则就几份文件，全读不贵。RAG会带来"改一条要重新入库、可能出同步bug"。等规则长到几十份再升级。

## 四、服务器目录结构（照建）

```
company-rules/                       ← 规则区（目录名公司定）
│
├── 规则/                            ← 【只读区】机器人只能读
│   ├── 公司/                        第1层 · 全公司（所有机器人读）
│   │   └── 公司层_通用底座.md
│   └── 岗位/                        第2层 · 岗位（只有本部门读）
│       └── sales/
│           └── 销售层_岗位规则.md
│
├── 积累/                            ← 【可写区】机器人可写
│   ├── sales/                       销售部部门层积累
│   └── 个人/                        第3层 · 个人积累
│       └── <userid>/                按发送人userid分开存
│
└── 提规则/                          ← 【人写区】只有人写，机器人既不读也不写
    └── sales/                       岗位负责人想加/改规则，在这写文件
```

### ⚠️ 三个区必须分开，这是权限的分界线

| 区 | 放什么 | 机器人权限 |
|---|---|---|
| **规则/** | 怎么干、底线在哪 | **只读**。绝不可写、改、删 |
| **积累/** | 台账、经验、干过的活 | **可写**。这是它的工作记忆 |
| **提规则/** | **人**想加/改的规则建议（待负责人确认） | **完全隔离**：既不读也不写 |

**为什么分开**：
- 规则区能让机器人写 = 它自己给自己放权（公司已定：纠偏必须由人做）
- 积累区不让机器人写 = 它每天干的活存不下来，等于死的
- **提规则区必须对机器人完全不可见** = 里面是**还没被确认的草稿**。机器人能读到，就会把没确认的东西当规则执行——**没被确认的规则，对它必须不存在**

**文件从哪来**：`规则/` 内容由公司提供（sandy），技术团队无需编写。`积累/` 和 `提规则/` 初始化空目录即可。

## 五、权限（最关键 · 必须锁死）

| 目录 | 对象 | 读 | 写/改/删 |
|---|---|---|---|
| **规则/** | **机器人** | 允许 | **禁止** |
| **规则/** | 人 | 允许 | 允许 |
| **积累/** | 机器人 | 允许 | **允许** |
| **积累/** | 人 | 允许 | 允许 |
| **提规则/** | **机器人** | **禁止** | **禁止** |
| **提规则/** | 人 | 允许 | **允许** |

**实现要两层都做（缺一层不算锁）**：

| 层 | 锁什么 | 怎么做 |
|---|---|---|
| **第1层 文件系统** | 机器人那个系统账号对 `规则/` **只能读** | `chmod -R a-w 规则/`，或只读挂载；机器人不要用 root 跑 |
| **第2层 机器人工具** | 机器人手里**根本没有"写文件"工具**（至少对规则区没有） | 工具白名单 / 禁止文件写入工具指向规则区 |

**为什么必须两层**：
- 只做第1层 → 万一机器人以更高权限跑（如被配成root），锁形同虚设
- 只做第2层 → 机器人若换个方式调系统，仍可能碰到文件

**⚠️ 敏感信息的物理隔离（销售层特有）**：
销售层有合同金额/客户名单。**HR机器人的账号对 `规则/岗位/sales/` 和 `积累/sales/` 必须不可读**——不是"只读"，是"看不见"。
如果所有机器人共用root、共用目录，那"岗位规则只有本部门能读"**在物理上就不成立**。规则写在提示词里说"别看"，没有用。

## 六、可用性要求（断机不许失忆 · 必备项）

**数字员工不是"一个虚拟机"，是跑在服务器上的一个进程。** 进程会死，这正常。但它必须**死了能回来、回来还记得事**。

### 必备项1：进程自动拉起
- 崩溃/重启后**自动重新启动**，员工侧无感知
- 做法不限：systemd、supervisor、Docker restart 策略都行
- **不接受**"挂了要人工上服务器手动启动"
- 验收：**手动 kill 掉进程，等30秒，看它是否自己回来**

### 必备项2：记忆必须落磁盘（最关键）
- `积累/` 内容**必须写磁盘持久化存储，禁止只存内存**
- 纯文件最稳；用数据库必须**持久化数据库**，**绝不可用内存数据库**（重启即清空=集体失忆）
- 验收：**写一条记录 → 重启进程 → 看记录还在不在**

### 必备项3：多机器人隔离
| 隔离项 | 要求 |
|---|---|
| 系统账号 | 每个数字员工**用自己的系统账号跑**。严禁全部用 root |
| 目录权限 | 别的部门账号对销售目录**必须不可读**（不是只读，是看不见） |
| 对话存储 | 每个人的对话**按 userid 分开存**，绝不混在一个存储里 |

### 必备项4：`积累/` 的存储形态要确认
请明确 `积累/` 用的是哪种：**(a) 纯文件（推荐）** / (b) 持久化数据库（可以） / **(c) 内存数据库（不行，必须改）**

## 七、企微接口（技术团队接这些）

| 编号 | 要求 | 说明 | 优先级 |
|---|---|---|---|
| T1 | **透传发送人 userid** | 机器人靠这个"认人"、分开记忆；**没有这条，私聊按人分开记忆做不了** | **P0** |
| T2 | 单聊消息收发 | "销售助理"号能被同事单聊、能回复 | P0 |
| T3 | 群聊 @机器人 | 部门群里 @ 即触发 | P0 |
| T4 | 文件收发 | 同事能发文件给机器人，机器人能回文件 | P0 |
| T5 | 知识库挂载/检索 | 能挂知识文档，机器人按需检索 | P1 |
| T6 | 记忆读写接口 | 个人层/部门层记忆存取（可先落一个库，按 userid 分区） | P1 |
| T7 | 权限与审计 | 谁能看部门层、个人层不外泄的管控与日志 | P2 |

> **判断**：T1～T4 是关键。**缺 T1，私聊就退化成"一个人"**，两个入口的意义就没了。

## 八、机器人行为底线（已写进各层文件，供技术核对）

1. **规则区是权威**：与自己理解冲突时，以规则区为准
2. **不确定必须说**：医院名/医生姓名/案例数据/证号/政策原文/数字 → 标"请核实"，宁说不知道不许编
3. **不自行输出规则区没有的对外结论**
4. **收到纠偏 → 记录并上报人，不自行改规则**
5. **重启后先读 `积累/`**
6. **不落盘 = 没干过**
7. **半截的活不许当成品交**

## 十、要技术团队回话的五件事

1. **目录建在哪个路径？**
2. **机器人是哪个框架**（决定怎么拼 system prompt）？
3. **企微入口怎么给同事用**（手机 + 电脑）？
4. **多个机器人怎么部署**？
   - (a) 手写独立进程（各自 systemd/supervisor）→ 按"每进程独立系统账号"写
   - (b) Docker/容器 → 按"每容器独立挂载、禁共享目录"写
   - **两条都行，但要说清是哪条**——这决定权限锁怎么落
5. **`积累/` 用什么存储**？纯文件 / 持久化数据库 / **内存数据库（不行，必须改）**
