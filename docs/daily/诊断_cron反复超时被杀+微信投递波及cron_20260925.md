- **日期**：2026-09-25 00:2x
- **发现者**：小龙虾（本地 Hermes），job `306b06dd1ba7`（协同接活-避峰）

## 1. 现象（两条独立但相关的故障）

### 1.1 故障 A：cron job 反复被 inactivity 看门狗杀掉

`~/.hermes/logs/gateway.error.log` 中，两个 job 反复报：

```
ERROR cron.scheduler: Job '小龙虾-协同接活（避峰 每90m，仅空闲段）' idle for 701s (inactivity limit 600s)
  | last_activity=executing tool: terminal | iteration=1/90
TimeoutError: Cron job '...' idle for 701s (limit 600s)
```

**对 `协同接活` 一个 job 的 `idle for` 失败行，实测 count = 114 次**（跨 06-18 建仓至今）。

`last_activity` 分布（读全量失败行归纳）：

| last_activity | 说明 | 占比直觉 |
|---|---|---|
| `executing tool: terminal` | 多数 | 最高 |
| `waiting for stream response (XXXs, no chunks yet)` | **模型流卡死** | 高 |
| `stale stream detected after 180s, reconnecting` | **模型流卡死并触发重连** | 中 |
| `executing tool: patch / write_file / search_files` | 工具执行期间卡住 | 中 |
| `starting API call #N` / `initializing` | **API 调用起点即卡** | 中 |
| `receiving stream response` | 收流中卡死 | 低 |

idle 时长实测跨度 **610s ~ 3654s**（上限 600s）→ 一旦卡住就不会自愈，必被杀。

## 2. 根因判定（分层）

### 2.1 故障 A 的直接根因 = **模型 API 流卡死（provider 侧）**，不是某个工具挂起

- 决定性证据：失败行里 `last_activity=waiting for stream response (936s, no chunks yet)` 与
  `stale stream detected after 180s, reconnecting` —— **这是流式响应一个 chunk 都收不到**，属**上游 provider（deepseek）侧的连接/流停滞**，非本地工具问题。
- 次证：`starting API call #N`（发起就卡）、`initializing`（初始化就卡）—— 说明卡点在**发起/接收 API 调用**，与具体工具无关。
- 佐证：`last_activity` 里 `terminal/patch/write_file/search_files` 混杂出现、无单一工具相关性 → **同一根因（API 层）在随机时点表现**。
- 旁证：同日志多次 `WARNING gateway.run: Shutdown diagnostic`（gateway 被重启），重启后 job 恢复 `last_status=ok` → 说明**卡死态在进程重启后清除**，符合\"流/会话层卡死\"特征。

### 2.2 故障 B 根因 = 已在 09-21 诊断中定性的 weixin 会话级损坏（同引用文档 §3/§4）

- 09-21 结论：网络一抖 → weixin 适配器重连重建 aiohttp session → `send_message` 复用活适配器时命中跨-Task 超时上下文 → 3 次重试全打在坏 session 上 → **该错误在 gateway 进程生命周期内不可自愈，须重启 gateway**。
- 本次新增证据：该错误串**已出现在 `cron.scheduler` 的 delivery 路径**（见 §1.2），证实波及面包含 cron 自动投递。

## 3. 已造成的实际损失（本轮实测）

1. **09-24 晚间 ~6.5h 零 cron 会话**：会话文件实测 `13:37 → 19:44` 之间**无任何 cron session**（应是 18:25/18:37/19:07/19:25/19:37 五个排班轮），而这两个 job 的 cron 表达式（`25 0-8,12,13,18-23` / `7,37 0-8,12,13,18-23`）**明确覆盖 18/19 点** → **5 个协同/自愈轮次静默丢失**。
2. **幸运点**：`~/echoes` 工作区核对为**干净、无孤儿半成品文件**（丢失的轮次都在写文件前就被杀）→ **无脏数据残留**，无需清理。
3. **对协同的影响**：丢的是**监控轮**，不是新任务轮；但意味着**那 6.5h 内若对方派单/发回执，我侧没有按时发现**（本轮 00:2x 已补扫，确认队列 `小龙虾请做_*`=0、无待响应项）。

## 4. 现有可用旋钮（供拍板，不擅自改）

- `cron/scheduler.py:1034`：`_cron_timeout = float(os.getenv("HERMES_CRON_TIMEOUT", 600))`
  → 可通过环境变量**放大 inactivity 上限**。
  ⚠️ 但**单纯放大上限是坏主意**：卡死时不杀 = 白烧 token + 长时间占住调度器（实测有 `idle for 3654s` 的实例），且不能让卡死的流恢复。
- `cron/scheduler.py:1096`：超时后 `agent.interrupt("Cron job timed out (inactivity)")` → 会中断，但**本轮工作可能半途**（历史上 09-24 12:50 那次即\"写回执时被打断\"，后由自愈轮补提交）。

## 5. 为什么不自修（依铁律 0-C / 四点七第 3 条）

| 维度 | 判断 |
|---|---|
| 文件归属 | `~/.hermes/hermes-agent/` = **上游第三方代码**（本地 `main` 落后 origin 上万 commits）；改它=维护分叉 |
| 生效条件 | 任何修复都需**重启生产 gateway** 才生效 = 铁律 0-C 危险动作 |
| 失败代价 | gateway 是 sandy **唯一**微信通道；错改会彻底断链 |
| 旋钮风险 | `HERMES_CRON_TIMEOUT` 放大上限会**制造长时间空烧**，非净收益 |

→ 结论：**只记录 + 上报，给修复方向供 sandy 拍板。**

## 6. 建议修复方向（待 sandy 决策，风险由低到高）

1. **最快止血（无代码改动）**：**重启 gateway** ≥ 每日一次/发现投递失败时立即重启 —— 可同时清掉 2.1 的卡死态与 2.2 的坏 session（按 09-21 结论，故障 B 在进程内不可自愈）。
2. **故障 A 加固（中）**：给\"流式响应 N 秒无 chunk\"加**主动重建连接/重试**（日志已有 `stale stream detected after 180s, reconnecting` 的机制，但显然**未能恢复**）→ 排查为何重连后仍卡；或对 cron 任务**降级为非流式/短超时**请求，避免长流卡死。
3. **故障 B 加固（小、稳）**：按 09-21 诊断 §6 第 2/3 条改 weixin（不复用活 `_send_session`；坏 session 先重建再重试）。
4. **可观测性（零风险、建议必做）**：`self_healthcheck_v2` 目前**未监控 cron 成功率与投递成功率** → 建议加\"最近 24h cron 失败数 / 投递失败数\"指标，否则该类静默故障**无人告警**（本次就是靠人工翻日志才发现）。

> 任何代码改动都建议先在隔离环境验证，再决定是否重启生产 gateway 上线。
