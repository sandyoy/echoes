## 〇、一句话说清这是什么

> **这不是一个"记录工具"，是一台"出书机"。**
>
> 老人（或子女）把一辈子的**文字、照片、视频**放进来 → 系统**按时间轴**把它们编成**一本书** → 这本书**可以卖钱、可以印出来、可以寄到手上**。

旧版做的是"记下来"，新版做的是"**记下来 → 编成书 → 卖出去 → 寄到家**"。

## 一、完整业务流程（严格按 sandy 口述，不加料不改写）

### 流程总览

```
① 采集          ② 编排              ③ 成书            ④ 收付款          ⑤ 制作交付
文字             按时间轴            电子书            扫码支付          印刷制作
照片      ──→    调整顺序     ──→    实体书     ──→    订单成立   ──→    物流邮寄
视频             补章节/封面          两种形态           （可选）          状态可查
```

### 逐步说明

#### ① 采集 —— "我需要加图片、加照片、加视频"

- **文字**：手打字 / 语音说话转文字（老人主要用嘴，不用手）
- **照片**：一次一张或一次多张，可以随时回来补
- **视频**：一段或多段，可以随时回来补
- **语音原声**：说话的原声保留（老人听到自己声音会感动，也是珍贵素材）
- 关键要求：**老人操作要极简**。一句话能录、一张照片能传，不能有"填表单"的感觉。

#### ② 编排 —— "这些文字和这些视频可以按照时间轴的方式组成"

- 所有素材（文字/照片/视频）**按时间归位**到时间轴上
- 时间轴是**主视图**，也是**书的目录**
- 素材要能：**调整顺序、归类到章节、选封面**
- 关键要求：老人照片顺序可能乱、年份可能记不清 → 必须容错（"记不清年份"要有兜底，不能卡死）

#### ③ 成书 —— "是一个时间轴列表的一本书"

书有两种形态，**都要支持**：

| 形态 | 说明 | 交付方式 |
|---|---|---|
| **电子书** | 手机上能翻、能看视频、能放大照片 | 生成后直接看/分享 |
| **实体书** | 印刷装订成册 | 制作 → 物流 → 邮寄到家 |

书的构成：
- **封面**（可换、可自己上传照片做封面）
- **章节**（按年份分 / 按主题分，可自定义）
- **正文**（图文混排：文字 + 照片 + 视频位）
- **后记/落款**（可选）

#### ④ 收付款 —— "这本书的话，扫码还能够支付钱"

- **扫码 → 支付 → 订单成立**
- ⚠️ **重要边界（sandy 明确）**：**"我收不收钱，那是我的事情"** ——
  - 系统只负责**提供收付款的能力**，不替 sandy 决定：卖不卖、卖多少钱、收给谁
  - 因此这一块**做成"可开关"的**：可以纯免费送（不收款），也可以收费
  - 收款主体、费率、分账规则 → **待 sandy 定，不定死**
- 需要支持的形式（预留，具体待定）：
  - 微信支付（小程序内原生）
  - 可能的其他方式（待定）

#### ⑤ 制作与邮寄 —— "还能够去制作出来，然后邮寄给他们"

- 实体书：下单 → 印刷制作 → 打包 → 物流 → 邮寄到指定地址
- 电子书：支付后直接解锁/交付
- **订单状态全流程可查**：已下单 / 制作中 / 已寄出 / 已签收
- 收货地址：由下单人填写（可能是子女给老人买，地址不一定是下单人的）

## 二、为什么旧的要全拆（sandy 的判断依据）

| 旧版能做的 | 新版必须有的 | 差距性质 |
|---|---|---|
| 一条回忆 = 纯文字 + 一段语音 | 一条回忆 = 文字 + **多张照片** + **多段视频** + 语音 | **数据模型根上不同** |
| 没有"书"这个概念 | 有**书**这个实体，回忆归属于书 | **缺一整个实体** |
| 时间轴只用来排序 | 时间轴 = **书的目录/章节结构** | **用途升级** |
| 无支付 | 扫码支付 → 订单 → 制作 → 物流 | **缺一整条商业链** |
| 无排版 | 出书排版（封面/章节页/图文混排） | **缺一整个模块** |

**结论**：旧版地基只能盖平房，新版要盖楼。**楼板（数据结构）现在就得浇，补是补不上的。**

## 三、系统设计（给小鲸鱼的技术框架建议）

> 以下为技术建议，**具体实现由小鲸鱼定**，此处只列不可绕过的硬约束。

### 3.1 数据模型（核心，必须一次做对）

```text
User（用户）
  └── Book（书）★核心实体，旧版没有
        ├── id / 标题 / 封面
        ├── ownerId（谁的书）
        ├── createdAt / updatedAt
        ├── status（草稿/已完成/已下单/已印制/已寄出）
        └── chapters[]（章节，可空=不分章）
              └── Story（一条回忆）
                    ├── id / content（文字）
                    ├── eventYear / eventDate（事件年份★旧版缺陷点）
                    ├── media[]（★核心新增）
                    │     ├── type: photo | video | audio
                    │     ├── url / localPath
                    │     ├── order（在同一条回忆内的顺序）
                    │     └── caption（配文，可选）
                    ├── audioPath（语音原声）
                    └── createdAt
```

### 3.2 三大硬约束（绕不过）

1. **`Book` 实体必须单独存在** —— 不能靠"把所有 story 捞出来排一排"代替，否则无法出书、无法下单、无法邮寄
2. **`Story.media[]` 必须是数组** —— 一条回忆配多张照片/多段视频，旧版是单值，必须改
3. **`Story.eventYear` 必须独立于 `createdAt`** —— 讲 1975 年的事要落在 1975，不能落今天

### 3.3 页面结构（建议）

```
首页          —— 入口：继续记录 / 看我的书
记录页        —— 打字 / 说话 / 加照片 / 加视频（极简，一屏搞定）
时间轴页      —— 主视图，所有素材按年归位（= 书的目录）
编排页        —— 调整顺序 / 分章节 / 选封面
书预览页      —— 翻页看书（电子书形态）
下单页        —— 选形态（电子/实体）→ 填地址 → 支付
订单页        —— 查进度（已付/制作中/已寄出）
我的页        —— 我的书 / 我的订单 / 设置
```

### 3.4 技术栈建议（沿用现状，不折腾）

- 前端：微信小程序（现有 `miniprogram/`，**重用骨架但重写数据层**）
- 后端：现有 `https://yuanaikang.cn/api`（Node/Python 均可，小鲸鱼定）
- 媒体存储：照片/视频要有可靠存储（本地 + 云端），**不能让老人辛苦录的东西丢**
- 语音识别：讯飞（老人方言/抗噪强，sandy 已给 key）
- 支付：微信支付（小程序原生，商户号待 sandy 提供）

### 3.5 媒体存储策略（关键，直接决定用户体验）

| 类型 | 策略 | 理由 |
|---|---|---|
| 文字 | 本地必存 + 云端同步 | 量小，必须绝不丢 |
| 语音原声 | 本地必存 + 云端异步传 | 是珍贵素材，弱网也要留住 |
| 照片 | 本地必存（原图）+ 云端压缩传 | 一张几 MB，弱网必须能存下 |
| 视频 | **本地必存 + 明确提示"上传中"** | 视频大，必须让用户看到进度，不能静默吞 |

**铁律**：任何素材**本地先落地，再谈上传**。上传失败不阻断用户，但要有明确状态提示。

## 五、分阶段交付建议（待 sandy 定优先级）

> 完整链路很长，建议分期，每期都能"看得见东西"。

| 期 | 内容 | 交付物 | 预估 |
|---|---|---|---|
| **一期** | **采集 + 时间轴**（文字/语音/照片/视频能进来，按年归位） | 能完整记录一条（带照片） | 先走通 |
| **二期** | **成书 + 预览**（编排、分章、封面、电子书翻页） | 能看到自己的书 | — |
| **三期** | **收付款**（下单、支付、订单状态） | 能下单付款 | 需商户号 |
| **四期** | **实体制作 + 物流**（接印刷厂、物流、邮寄） | 书寄到家 | 需谈供应商 |

⚠️ **三、四期依赖线下资源**（微信支付商户号、印刷厂、物流），**不是纯写代码能解决的**，需要 sandy 那边先落地商务。
