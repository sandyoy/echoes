## 三、三个必须先补的漏洞（sandy 要的"出题逻辑"卡在这）

### 漏洞 1（最要紧）：线上根本没有出题逻辑

我 grep 了你这次的文件，题目来源还是这行：

```js
const QIDS = Array.from({length:23},(_,i)=>'a'+(i+1));   // a1~a23 死写的23题
```

**线上版没有 `quizzes/dayN.json`、没有按天切换、没有知识点树接入。** 你自己在派工单第 136 行也写了：

> 「题目按天出（`quizzes/dayN.json`）：本地版已做，线上版还没做，下一批」

sandy 的原话是「**他编了一个出题逻辑**」「**因为以后出题呢是由他那边在出**」。他要的是：**你那边能持续出新题，线上跟着走**，不是固定 23 题。

**所以这次一起传的，必须是带出题逻辑的版本。** 否则传上去他还是看到一样的 23 题，会认为没做完。

### 漏洞 2：`dayN.json` 这个方案本身就不可持续

`sandy` 要的是"**长期每天有新题**"。如果每天你手工写一个 `dayN.json`：

- 你哪天没写，那天就没题
- 200 天后就是 200 个文件
- 改一次规则要改 N 个文件

**我的建议（你可以推翻）**：不要按天出静态文件，改成**按知识点树 + 进度算出来**。

你已经把 `数学_知识点树_v1.0_20261118.md`（195 个知识点）和 `00_规则_教学结构定稿_v2.0` 定稿了——**这两份是资产**，应该让它们真正驱动出题，而不是变成两份躺在仓库里的文档。

具体可以是：`GET /xiaoqiao/api/quiz?day=N` → 后端按规则从知识点树算当天该出哪些题 → 返回题目数组。这样：
- 不用你天天写文件
- 规则改了，历史/未来一起变
- 小桥的进度从数据库读，能接上他昨天错在哪

### 漏洞 3：判分接口有了，但没用上「昨天错在哪」

现在 `api/grade` 只判对错、给分。但**一个老师真正的价值是记住孩子昨天错在哪，今天专门补。**

你 11-18 那版批改单里写的是"只判对错不重讲"，这在当时是对的（先让流程跑通）。但下一步必须做：

- 把错的题号 + 知识点记下来
- 第二天出题时**优先出同一知识点的变式题**
- 这才是"老师"，不然只是个判卷机

**这条不是这次必须做，但请你在设计出题逻辑时预留接口**，别做成一次性算完就扔。
